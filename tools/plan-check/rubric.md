# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause (Diagnosis section, or opening statement if no heading exists) read against the repro evidence block's steps, artifacts, and control runs | The stated cause is consistent with what the repro evidence demonstrates; passes if the plan's mechanism is not directly ruled out by any control run in the repro evidence. Fails if the plan names a cause that the package's own control runs show is not the trigger. Specifically: if a control run shows the named mechanism works correctly in isolation or in a non-triggering context, and the failure only occurs in a specific calling context or surrounding condition, then a diagnosis that blames the mechanism itself (rather than the calling context or context-setting infrastructure) is contradicted and fails. Example: if the control shows `[.a]` at the top level correctly produces `[null]` but the plan says "the collect operator is the defect" — the control has shown the operator works; the defect is in how it is called from within the condition context, not in the operator itself | required |
| scope-bounded | The plan's in-scope and not-in-scope statements (or the full list of proposed changes if no explicit scope section exists), read against the issue description | The plan addresses one bounded change targeting the reproduced failure without bundling drive-by refactors, migrations, redesigns, or unrequested features; passes if every significant work item in the plan is required to fix the reproduced behavior. Fails if the plan adds substantial work the issue never asked for — a new abstraction layer, a dependency upgrade, a settings panel, a test-harness migration, or any "while we're here" rewrite that would not be needed to close the reported failure | required |
| executable | The plan's files or code areas, approach, and steps read alone — no other sources | At least one specific file path, module, or code area is named and an approach is described in enough detail that a stranger could begin executing it without asking the author. Naming a module or code area with a specific described approach passes even if exact function names are deferred pending active debugging already underway; the bar is "where to look and what to do," not "every function name." Fails if zero files or code areas are named, if the approach is entirely "investigate and see what I find," or if every key implementation decision is explicitly deferred to build time with no current direction | required |
| decisive-test | The plan's test plan section read against the repro evidence's steps, commands, and observable artifacts | The test plan names at least one concrete, runnable check that directly verifies the fix works — a specific command to run, an expected exit code, or an observable output change tied to the failure the repro demonstrated. Fails if the test plan describes only a subjective feeling ("should feel faster," "nothing else should break"), says only "run the test suite" with no specific expected outcome for the fix itself, or names no test at all | required |
| thread-aware | The plan comment read against the thread highlights (maintainer comments from OWNER, COLLABORATOR, or MEMBER) and against the repo-facts contribution policy field | Passes if the plan comment does not ignore explicit maintainer direction present in the thread highlights (a named culprit, a stated fix approach, a testing request, or a prior-art PR to engage) and if the repo's AI disclosure requirement is satisfied. A maintainer-identified culprit or fix location must be engaged — acknowledged, built on, or explicitly departed from with a reason; silence is not engagement. For AI disclosure: if the repo-facts policy uses language like "all AI usage must be disclosed" or "AI-assisted contributions must disclose," it is a blanket requirement; in eval mode, treat every package as AI-assisted, so absence of disclosure under a blanket policy fails. Policies that require only human voice or human responsibility (not an explicit disclosure statement) pass when the comment reads as human-authored | required |

## Verdict rule

Accept if every required check passes. Reject if any required check fails. `unclear` counts as fail: a plan whose evidence cannot be verified from the package is not ready to build from.
